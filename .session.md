43. ## Introduction
44. 
45. ### Getting Started
46. To get started, you can open and play around with the sample sessions in the *Help* menu.
47. 
48. The sample sessions can also be used as templates - saving a session As... copies all the dependencies to the new location.
49. 
50. ### Session
51. In order to try out the shaders, the session allows to define draw and compute calls, together with the pipeline state and data the programs should operate on.
52. 
53. It can be populated with items from the *Session* menu or the context menu. Undo/redo, copy/paste and drag/drop should work as expected (also between multiple instances).
54. It is even possible to drag the items to and from a text editor (they are serialized as JSON).
55. 
56. ### Evaluation
57. The session can be evaluated manually *[F6]*, automatically whenever something relevant changes *[F7]* or steadily *[F8]*, for animations.
58. All items which contributed to the last evaluation are highlighted.
59. 
60. ### Items
61. The items of a session pretty much correspond the concepts known from writing OpenGL or Vulkan applications:
62. 
63. - **Call** -
64. Most prominently are the draw, compute and ray trace calls. Whenever the session is evaluated, all active calls are evaluated in consecutive order. They can be de-/activated using the checkbox.
65. The elapsed time of each call is output to the *Message* window (measured using GPU timer queries).
66. 
67. - **Program** -
68. Consists of one or multiple shaders, which are linked together, so they can be used by draw or compute calls.
69. 
70. - **Texture** -
71. All kind of color, depth or stencil textures can be created. They serve as sample sources, image in- and outputs and target attachments. They can be backed by files.
72. 
73. - **Target** -
74. Specifies where draws calls should render to. Multiple images can be attached. Depending on the attached image's type, different render states can be configured.
75. 
76. - **Binding** -
77. Allows to bind data to a program's uniforms, samplers, images and buffers. A binding affects all subsequent calls, until it is replaced by a binding with the same name, or the scope ends (see *Groups*). The name of a binding needs to match the name of a program's binding point.
78. 
79. - **Buffer** -
80. Buffer blocks define the structure of a region within a binary. They consist of rows with multiple fields of some data type. Buffers can be backed by binary files.
81. 
82. - **Stream** -
83. Serves as the input for vertex shaders. A stream consists of multiple attributes, which get their data from the referenced buffer blocks.
84. 
85. - **Group** -
86. Allows to structure more complex sessions. They open a new scope unless *inline scope* is checked. Items within a scope are not visible for items outside the scope (they do not appear in the combo boxes).
87. 
88. - **Script** -
89. Allows to define JavaScript functions and variables in script files, which can subsequently be used in uniform binding expressions.
90. Scripts can also be used to dynamically populate the session and generate buffer and texture data.
91. There is one JavaScript state for the whole session and the scripts are evaluated in consecutive order (*Group* scopes do not have an effect).
92. 
93. - **Acceleration Structure** -
94. Allows to define the instances and geometry for ray tracing calls.
95.
